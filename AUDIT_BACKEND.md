## 3. Jobs queue

**States** (`JobStatus` enum): `pending`, `processing`, `done`, `failed`.

**Transitions**, all in `src/worker.ts`:
- Created as `pending` (`segments.ts` on confirm, `transcribeSegment.ts` on
  its own completion).
- Claimed: `UPDATE jobs SET status='processing' ... WHERE id = (SELECT ...
  FOR UPDATE SKIP LOCKED) RETURNING *` — one row, oldest `created_at` first.
- On handler success: `status: "done"`.
- On handler throw (any error, from any stage): `status: "failed"`,
  `attempts: {increment: 1}`, `last_error: <formatted error string>`.

**Retry: there is none.** `attempts` is incremented on every failure but
**nothing in the codebase ever reads that field** or re-queues a failed job
back to `pending`. A failed job stays `failed` forever unless a human
manually resets its row in the database. There is no backoff, no max-attempts
cutoff, no dead-letter table — because there's no retry loop to cap in the
first place.

**Stuck jobs**: if a worker process claims a job (row moves to `processing`)
and then the process crashes, is killed, or loses its DB connection before
finishing, **the job stays in `processing` permanently**. The claim query
(`WHERE status = 'pending'`) will never select it again — no other worker
will pick it up, there's no visibility timeout, no heartbeat, no janitor
process. This is a real, currently-unhandled failure mode, not a theoretical
one — the worker blocks synchronously for the entire render duration (up to
10 minutes, see §5), so a crash during that window produces a silently stuck
job with no automatic recovery path.

**No monitoring**: failures surface only via `console.error` in whichever
process's log currently has them. No alerting, no failed-job listing
endpoint, no dashboard.

**Job types**: exactly two (`JobType` enum) — `transcribe_segment`,
`render_segment`. The handler dispatch in `worker.ts` is a
`Record<string, handler>` map; an unrecognized `job.type` string would just
get marked `done` with no work performed (no handler found → falls through
to the success path).

**Concurrency**: `SELECT ... FOR UPDATE SKIP LOCKED` is the actual mechanism
— confirmed safe under real concurrent load in `BUILD_STEPS.md`'s step 5
verification (1500 jobs, 2 workers, zero double-claims). Poll loop is 1s when
idle, immediate re-poll (`setImmediate`) after a successful claim — a
backlog gets drained continuously, not on a fixed interval.

## 4. Transcription pipeline, end to end

`transcribeSegmentHandler` in `src/jobs/transcribeSegment.ts`:

1. `Segment.status` → `"transcribing"`.
2. Create a local temp directory (`node:os` `tmpdir()` + `mkdtemp`).
3. **If no `Transcript` row exists yet:**
   a. Get a presigned S3 GET URL for the raw segment video; `ffmpeg` (shelled
      out via `execFile`, HTTP range-reads directly from the URL, no full
      download) extracts audio to a local `.mp3`.
   b. POST that file to ElevenLabs Scribe (`scribe_v1` model, word-level
      timestamps) via native `fetch`/`FormData`.
   c. Build SRT and VTT text from the word timestamps (`services/captions.ts`,
      10-word cues), upload both to S3.
   d. Write the `Transcript` row (`text`, `language_detected`, `srt_key`,
      `vtt_key`).
4. **If the captioned video doesn't already exist in S3** (deterministic key,
   existence check is the idempotency guard, no DB column tracks it):
   a. Presign the raw video and the `.srt` for download; fetch the SRT text,
      write it to a local file.
   b. `ffmpeg` burns it onto the raw video (`subtitles` filter) →
      `captioned.mp4` locally.
   c. Upload `captioned.mp4` to S3 at the deterministic key.
5. **If no `SentimentResult` row exists yet**: call Gemini
   (`analyzeSentiment`), write the row (see §6 for fields).
6. `Segment.status` → `"transcribed"`.
7. Queue a `render_segment` job — guarded against duplicates by checking for
   an existing job with the same `segment_id` in its payload first.
8. On any thrown error at any stage: `Segment.status` → `"failed"`, temp dir
   removed (`finally`), error re-thrown (caught by `worker.ts`, which marks
   the *job* `failed` — see §3).

Idempotency is per-stage-result, not per-job — a retried job skips whatever's
already written. This only matters in practice for a **manually** re-queued
job, since nothing auto-retries (§3).

External dependencies this pipeline needs at runtime: the `ffmpeg` binary on
`PATH`, network access to ElevenLabs, network access to Gemini, network
access to S3 — none of these are checked for availability at startup, only
discovered when a job actually fails.

## 5. Render pipeline, end to end — including exactly where it stops

`renderSegmentHandler` in `src/jobs/renderSegment.ts`:

1. Load the `Segment` with its `distributor` and `distributor.client`
   (for `branding_config`).
2. If a `RenderedVideo` row already exists with `status: "rendered"`, return
   immediately (idempotent short-circuit).
3. Look up question text + VO S3 key from `src/config/questions.ts` by
   `question_index` — **only indices 1–3 are configured**; 4 and 5 throw
   (`No question config for question_index N`).
4. Read `nexrender_template` out of `client.branding_config` (a `Json`
   column) — throws if absent.
5. Presign download URLs for the captioned video and the static VO audio.
6. Build a nexrender-cloud job payload: template id + hardcoded composition
   name `"MainComp"`, 4 assets (2 text layers, 1 audio layer, 1 video layer),
   an S3 upload block with explicitly-set `region`/`bucket`/`endpoint` and
   secret references (`${secrets.S3_ACCESS_KEY_ID}` etc., not raw values).
7. `POST /v2/jobs` to nexrender-cloud. Throws if the response has no
   `outputUrl`.
8. Extract the eventual S3 key from `outputUrl`, upsert `RenderedVideo` at
   `status: "rendering"` — **before the file exists**, this is deliberate
   (see §2/§ read-endpoint behavior).
9. `pollJobUntilDone` — polls `GET /v2/jobs/{id}` every 3s, **synchronously
   blocking this worker process**, up to a 10-minute timeout, then throws.
10. If the terminal status isn't `"finished"`: `RenderedVideo.status` →
    `"failed"`, throw.
11. If `"finished"`: `RenderedVideo.status` → `"rendered"`.

**Where it stops / what is unimplemented, concretely:**

- **Composition duration is fixed inside the nexrender template itself** —
  no duration parameter is sent in the payload at all; the code has no
  concept of "make this segment N seconds long." A 58-second source clip
  produced a 30-second render in real testing. This is a template-side
  limitation not addressed anywhere in this codebase.
- **No aspect-ratio/video normalization step exists.** Whatever ratio the
  phone produced is sent straight through as the `video` asset. A real test
  render came out visibly zoomed/cropped as a result. No ffmpeg pass, no
  scaling/padding logic anywhere in `renderSegment.ts` or `ffmpeg.ts`
  addresses this.
- **The render call is fully synchronous from the worker's perspective** —
  no webhook, no submit/complete split. One worker is unavailable for up to
  10 minutes per render.
- **No per-client template distinction** — both seeded `Client` rows point
  at the identical `nexrender_template` id in `prisma/seed.ts`. There is no
  code that would even support per-client branding beyond swapping that one
  string.
- **No retry on render failure** — same gap as §3; a failed nexrender job
  (timeout, template error, upload failure) leaves `RenderedVideo.status:
  "failed"` permanently with no automatic resubmission.
- **No caption styling configuration** — `burnCaptions` uses ffmpeg's
  `subtitles` filter with no `force_style` options; default styling only.
- **No compressed/small output variant** — the only artifact written to S3
  is nexrender's direct output (~45MB observed in testing). Nothing produces
  a WhatsApp-sized version.

## 6. Sentiment/analysis service

**Provider: Google Gemini**, via the `@google/genai` SDK
(`src/services/gemini.ts`), model string `"gemini-flash-latest"` (an
auto-updating alias, not a pinned version — hardcoded, no env override).
**Not Claude** — `GEMINI_API_KEY` is the actual required env var;
`ANTHROPIC_API_KEY` does not appear anywhere in the code. Code comments and
`CLAUDE.md` both describe this as a deliberate testing-phase substitution
that was never swapped back.

**Structured fields written** to `SentimentResult`, all produced by one
Gemini call using `responseMimeType: "application/json"` +
`responseSchema` (forced structured output, not prompt-parsed):
`sentiment_score` (number, -1 to 1), `themes` (string array), `summary`
(1–2 sentences), `best_quote` (verbatim excerpt), `is_relevant` (bool),
`moderation_flag` (bool — `true` means safe to publish), `contains_complaint`
(bool), `actionable_feedback` (nullable string, populated only when
`contains_complaint` is true), `highlight_score` (number, 0–1).

**Runs automatically**: yes, unconditionally, as stage 3 of
`transcribeSegmentHandler` — every segment that reaches the transcription
job also gets sentiment-analyzed in the same job run, no separate trigger,
no manual endpoint, no opt-out. Idempotency guard: only calls Gemini if no
`SentimentResult` row exists yet for that `segment_id`.

**Only consumer**: `GET /segments/sentiment`, scoped by `client_id` (not
`distributor_id`) — meaning any authenticated distributor can see every
other distributor's sentiment/moderation/complaint data under the same
client. This is called out in-code as acceptable for internal testing, not
as something to ship.

## 7. Environment variables and external dependencies

**Required** (`src/config/env.ts`, `REQUIRED_VARS` — startup throws if any
are missing): `DATABASE_URL`, `SESSION_SECRET`, `AWS_REGION`,
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `S3_BUCKET_NAME`,
`ELEVENLABS_API_KEY`, `GEMINI_API_KEY`, `NEXRENDER_SERVER_URL`,
`NEXRENDER_API_KEY`. All ten. `OPTIONAL_VARS` is currently an **empty
array** — nothing is actually optional in the running code today (an earlier
build-step note said `NEXRENDER_*` had been made optional; that is no longer
true in the current source).

`SESSION_SECRET` has an additional runtime check: throws at startup if under
32 characters.

`PORT` is not in `REQUIRED_VARS` — defaults to `3000` if unset or
non-numeric (`Number(process.env.PORT) || 3000`).

**External dependencies not covered by any env var:**
- `ffmpeg` binary must be present on `PATH` at runtime. No path is
  configurable, no version check, no presence check at startup — a missing
  binary only surfaces when a transcription job's `execFile` call fails.
- A reachable Postgres server — this repo only holds a connection string
  (`DATABASE_URL`); it does not start, manage, or containerize Postgres
  itself (no `docker-compose.yml`, no start script exists anywhere in the
  repo).
- Two separate long-running Node processes (API server, worker) must each be
  started manually — nothing in this repo supervises, restarts, or
  health-checks either one.

**Hardcoded values found in source** (not env-configurable):
- `COMPOSITION = "MainComp"` — nexrender composition name (`renderSegment.ts`).
- Question text (3 of 5 populated) and VO S3 key paths — `src/config/questions.ts`, plain object literals, not DB-driven.
- `SEED_ACCOUNTS` — 5 literal username/plaintext-test-password pairs
  (`ramesh`/`ramesh123` etc.) committed directly in
  `src/config/seedAccounts.ts`. Passwords are bcrypt-hashed before storage/
  comparison, but the plaintext test passwords themselves are visible in
  git history and the working tree.
- Rate-limit thresholds: 10 req/15min (login), 300 req/15min (global) —
  constants in `login.ts`/`index.ts`, no env override.
- Presigned URL expiries: 15min (upload), 15min (internal download), 1hr
  (playback) — constants in `s3.ts`.
- nexrender poll interval (3s) and timeout (10min) — constants in
  `nexrender.ts`.
- ElevenLabs model string `"scribe_v1"` — hardcoded in `elevenlabs.ts`.
- S3 `endpoint` for nexrender's upload config is derived from `AWS_REGION`
  (`https://s3.${AWS_REGION}.amazonaws.com`), not independently settable.

## 8. Local-machine assumptions

- **`ffmpeg` via `execFile`** (`src/services/ffmpeg.ts`) assumes the binary
  is already installed and on the host's `PATH`. There is **no Dockerfile
  anywhere in this repo** (confirmed via `git ls-files`), so there is
  currently no definition of a runtime image that would even guarantee
  `ffmpeg` exists in a deployed environment.
- **Temp files**: `transcribeSegmentHandler` writes to the OS temp directory
  (`node:os.tmpdir()` + `mkdtemp`) and cleans up in a `finally` block. This
  assumes a writable local/ephemeral filesystem, which is a reasonable
  assumption for a container but is still local-disk-shaped state — nothing
  here would survive or coordinate across multiple container instances mid-job.
- **No hardcoded `localhost`/`127.0.0.1` found anywhere in `src/`.** The
  server binds to all interfaces by default (plain `app.listen(config.PORT)`).
  `API_CONTRACT.md` documents that the mobile app currently reaches the
  backend over a LAN IP for same-wifi testing — that's a deployment-topology
  fact stated in docs, not something enforced or assumed by the code itself.
- **`.env` loading is dev-only and inconsistent between processes.**
  `npm run dev` and `npm run worker` both use `tsx --env-file=.env` — a
  local-dev mechanism. `npm run start` (`node dist/index.js`) does **not**
  load any `.env` file at all — it assumes env vars are already present in
  the process environment (correct assumption for App Runner's own env-var
  injection, but notably **there is no equivalent production start script
  for the worker** — only the dev-oriented `tsx --env-file` one exists;
  `npm run build` (`tsc`) would emit `dist/worker.js`, but no script invokes
  it with `node`).
- **No CI/CD configuration exists** — no `.github/workflows`, no other CI
  config found in the repo. Nothing runs tests, typechecks, or migrations
  automatically anywhere.

## 9. Account seeding vs. real provisioning

`prisma/seed.ts` creates exactly **2 `Client` rows and 5 `Distributor`
rows**, all literal hardcoded data — names, phone numbers, `invite_token`
strings, and `branding_config` JSON (including placeholder logo URLs like
`https://assets.example.com/ifb/logo.png`, which are not real assets).

`src/config/seedAccounts.ts` hardcodes 5 username/password pairs, each
mapped 1:1 to one of those 5 seeded distributors via its `invite_token` —
this **is** the entirety of Phase-A authentication.

**No provisioning flow exists.** There is no signup route, no invite-token
redemption route, no admin UI or API to create a new `Client` or
`Distributor`. The only way to add an account today is editing
`seed.ts`/`seedAccounts.ts` source files directly and re-running the seed
(or hand-writing SQL).

`Distributor.invite_token` exists in the schema and is clearly intended for
a future real invite-token exchange (Phase B), but **no code currently
issues, validates, or exchanges a token via any route** — today it's purely
an internal lookup key connecting a hardcoded login credential to its DB
row, not a functioning invite mechanism.

No password-change or password-reset capability exists anywhere.

No separate "admin" or "company" identity exists at all — the closest thing,
`GET /segments/sentiment`, is gated only by ordinary distributor auth
scoped to `client_id`, not a distinct admin role.

## 10. What's required for App Runner + RDS + S3 that doesn't exist yet

- **No Dockerfile and no App Runner build/runtime configuration** anywhere
  in the repo. App Runner needs either a container image or a supported
  managed runtime with explicit build/start commands — neither is defined.
- **No `ffmpeg` in any build artifact**, because there is no build artifact
  at all. App Runner's managed Node runtime does not include `ffmpeg`; this
  requires a custom Docker image, which does not exist.
- **No deployment story for the worker process.** App Runner is a
  request-driven web-service model; `worker.ts` is a persistent polling loop
  that structurally doesn't fit it (already noted in `learnings.md`). It
  would need its own always-on compute (e.g. Fargate task, small EC2
  instance) — no config, Dockerfile, or IaC for that exists in this repo.
- **No infrastructure-as-code at all** — no Terraform, CDK, CloudFormation,
  or any RDS/VPC/S3/IAM provisioning script. Networking between App Runner
  and RDS, the S3 bucket, and IAM policies are described only in prose
  (`docs/backend-plan.html`, `learnings.md`), implying manual/out-of-band
  setup that this repo has no record of.
- **No migration step wired into any deploy process** — `prisma/migrations`
  exist and are runnable manually via the Prisma CLI, but nothing in the
  repo runs them automatically as part of a deploy (no CI/CD exists to hook
  this into, per §8).
- **`/health` doesn't check anything** — it returns `200 {status:"ok"}`
  unconditionally, with no DB or S3 connectivity check. An App Runner health
  probe against this endpoint would report healthy even during a full
  database outage.
- **No secrets-management integration** — all config is read from
  `process.env` directly; there's no App Runner Secrets Manager / SSM
  Parameter Store wiring in code. Whoever deploys has to manually create and
  attach every secret (`SESSION_SECRET`, all API keys, DB credentials) to
  the App Runner service configuration; nothing here automates that.
- **No CORS configuration** — irrelevant today (only the mobile app calls
  this API directly), but would need adding before any browser-based client
  (e.g. the admin dashboard that doesn't exist yet — see below) could call
  it from App Runner's public URL.
- **Real per-client render templates don't exist** — not a deploy blocker,
  but both seeded clients currently share one placeholder nexrender
  template; shipping to real clients needs actual branded templates.
- **No admin dashboard** — flagged in `CLAUDE.md` as forgotten from scope
  entirely; still true, nothing has been built.
- **No observability beyond `console.log`/`console.error`** — App Runner
  captures stdout/stderr automatically, so logs aren't lost, but there's no
  structured logging, log levels, or request tracing beyond the ad-hoc
  `[stage] ... ms=N` lines already in the code.

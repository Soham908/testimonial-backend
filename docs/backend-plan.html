System overview

The shape of it, before the detail.

Postgres is the single source of truth for everything — not just data, but state. There's no separate queue system yet: a plain jobs table, polled by a background worker, does that job at this scale. Express stays thin — it issues presigned URLs, confirms uploads, writes rows, and reads them back. It never does the actual work of transcribing or rendering itself.

From the moment a segment is uploaded, two pipelines run independently and never block each other: a per-segment pipeline (audio → transcript → sentiment) and a per-distributor pipeline (five segments → branded reel). They only share one thing: the segment's own file, sitting in S3.

The mobile app never talks to S3, ElevenLabs, or Claude directly except for the one presigned upload — everything else it needs comes back through Express as a plain read.

End-to-end flow

Fans out into two independent pipelines after upload, fans back in at the read layer.

Identity & scoping

Two phases, one seam between them.

Phase A — now, testing only

Plain username/password login, 5 seeded dummy distributor accounts, no signup and no password-reset flow — this is test tooling, not a feature to build out. Worth seeding the 5 across two dummy clients rather than one, so client-level scoping actually gets exercised during testing, not just distributor-level. A POST /login issues a session token on successful auth.

Phase B — client-ready

A distributor's invite link carries an invite_token; the app exchanges it for a session credential on first open instead of a password.

Why the swap is cheap

Both phases end at the exact same place: one middleware, run on every route, resolves whatever credential came in into { distributor_id, client_id } and attaches it to the request. Every data-access function downstream requires that context as an argument, not an optional one — there's no code path that can query segments or transcripts without it already in hand. Because of that, moving from Phase A to Phase B only ever touches the login step itself — nothing about routes, scoping, or data access changes when the credential mechanism does.

Job pipeline

Two independent chains, both driven off the same jobs table.

Claiming a job safely

The worker claims a row with UPDATE jobs SET status='processing' WHERE id = (SELECT id FROM jobs WHERE status='pending' ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING * — a well-established Postgres pattern for exactly this, not an improvised shortcut. It's what makes "no Redis yet" a legitimate architectural choice rather than a corner cut, and it upgrades cleanly to a real queue later without changing how job payloads are shaped.

Per-segment (transcribe_segment)

Extract audio with ffmpeg → send to ElevenLabs Scribe for transcript + SRT/VTT → send transcript text to Claude for sentiment + themes → write both results → mark segment transcribed. Before calling either paid API, check whether a result already exists for this segment — a retried job must never re-transcribe or re-bill work that already succeeded.

Per-segment (render_segment)

Since each question gets its own branded reel rather than one merged video, this fires at the same point as transcribe_segment — as soon as that one segment is confirmed uploaded, not after all 5. Feeds nexrender with that single clip + client branding config (+ SRT captions once available), uploads the output, writes rendered_videos.

This also quietly resolves the stale-render problem flagged below — a retake just re-runs render_segment for that one question, the same overwrite-in-place pattern already used for segments and transcripts. Nothing merged, nothing to invalidate elsewhere.

Engineering principles applied

Not abstract advice — each one maps to a specific decision above.

01

Separation of concerns

Route handlers, job processing, and data access live in distinct layers. A change to how rendering works shouldn't risk touching how uploads are confirmed.

02

Idempotent job handlers

Every paid-API call checks for an existing result first. A retried job is always safe to re-run.

03

One source of truth for scoping

Distributor/client context resolved once, in one middleware, required by every data-access function — not re-implemented per route.

04

Fail-fast configuration

Required env vars (API keys, DB URL, bucket name) validated at process startup. A missing key crashes the server immediately and loudly, not confusingly mid-request later.

05

Migrations, never manual schema edits

Every schema change goes through Prisma migrate — reviewable, reversible, and readable as documentation.

06

Explicit state, not scattered booleans

Segment, job, and render status are all enums with defined values — "what's happening right now" is always answerable from one column.

07

Bounded retries

attempts and last_error on the jobs table mean a failing job retries a few times, then stops and surfaces — never loops forever, never silently vanishes.

08

Least-privilege, short-lived access

Presigned URLs are scoped to a single object key with a short expiry. The app itself never holds broad bucket credentials.

09

Traceable failures

Structured logging with job/segment id on every entry — working solo means a 2am failure needs to be diagnosable from a log line, not from memory.

Stack & rationale

ExpressAlready comfortable with it; heavily represented in Claude Code's training data
PostgresData is genuinely relational — distributor → segments → transcripts → sentiment
Prismaschema.prisma is reviewable as documentation, not just code
Postgres-backed jobs tableNo Redis needed yet — SKIP LOCKED is a real pattern, not a shortcut. Upgrades to BullMQ later without reshaping job payloads
S3Existing account and experience — R2's egress savings don't matter until real scale
AWS App Runner + RDSManaged deploy and TLS, no OS to patch, stays inside the one AWS account already in use

Open items to decide before coding starts

  1. S3 key naming convention — needs to be deterministic per segment (e.g. clients/{client_id}/distributors/{distributor_id}/segments/{question_index}.mp4) so a retake overwrites the same key rather than creating orphaned files.
  2. Presigned URL expiry — upload URLs should be short (~15 min); playback URLs can be longer-lived but should be freshly generated each time My Videos loads, not cached.
  3. Retry policy specifics — how many attempts before a job is marked failed, and what delay between them.
  4. Environment separation — settled for now: everything runs in dev only. Revisit before any real client data touches the system.
  5. Retention — how long raw segments stay in S3 after processing completes; ties directly into the compliance/consent work already planned. Deferred, discuss later.
  6. Seed data for Phase A — decide the 5 dummy accounts' details now, split across 2 dummy clients so client-level scoping gets tested, not just distributor-level.
  7. Local-cache sync check — confirm the segments read endpoint returns updated_at per segment by default, since the mobile app's local-first playback logic depends on comparing against it every time My Videos loads.
Build order once this is reviewed: schema and migrations first, then the upload + confirm endpoints, then the worker and per-segment pipeline, then the per-distributor render trigger, then the read endpoints My Videos depends on.
